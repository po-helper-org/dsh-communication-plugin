# Архитектура раздела: GoToSocial для ленты, Chatwoot для диалогов

Дата: 2026-09-11. Статус: дизайн согласован, к реализации не приступали.

Документ фиксирует разворот архитектуры раздела «Управление коммуникацией» и заменяет
собой решение от 2026-09-09, закрывшее
[issue #9](https://github.com/po-helper-org/dsh-communication-plugin/issues/9).

## Что изменилось в вводных

**Ограничение снято.** 2026-09-09 заказчик объявил раздел клиентским приложением без
выделенных серверов, и это структурно исключало Chatwoot. 2026-09-10 ограничение снято
заказчиком явно: выделенные серверы допустимы.

**Объём потока назван.** Telegram — 5–8 чатов, MTS.Link — около 100 чатов с постоянной
перепиской, почта — 10–50 писем в день. Порядка 5 000 сообщений в сутки, с запасом
считаем 10 000.

**Появились два режима представления.** Лента новостей поверх Phanpy и диалоги поверх
Chatwoot — это не одна панель с двумя вкладками данных, а два разных продукта под
две разные задачи.

## Решение

Раздел не хранит сообщения. Их хранят две системы, каждая под свой тип потока:

| Поток | Хранилище | Интерфейс |
|---|---|---|
| широковещательные каналы, новости | GoToSocial | форк Phanpy |
| личные диалоги, рабочие чаты и группы | Chatwoot | свой React поверх REST |

Раздел — **маршрутизатор и релей ответов**, а не хранилище и не Inbox.

```
   Telegram · почта · MTS.Link
              │
      ┌───────▼────────┐
      │   КОЛЛЕКТОР    │  состояние: курсоры, дедуп, outbox
      └──┬──────────┬──┘
   channel│          │user / chat
         ▼           ▼
  ┌────────────┐  ┌──────────┐
  │ GoToSocial │  │ Chatwoot │◄── вебхук ответа ──┐
  └─────┬──────┘  └────┬─────┘                    │
        │ Mastodon API │ REST API                 │
        ▼              ▼                          │
  ┌──────────────────────────────────┐            │
  │      ПАНЕЛЬ ХАРНЕССА (React)     │            │
  │  ┌────────────┐  ┌────────────┐  │            │
  │  │  Лента     │  │  Диалоги   │──┼────────────┘
  │  │ iframe →   │  │ свой React │  │
  │  │ форк Phanpy│  │ на REST    │  │
  │  └────────────┘  └────────────┘  │
  └──────────────────────────────────┘
```

## Почему SQLite уходит как хранилище сообщений

Раздел писал заявки в локальный SQLite, потому что больше писать было некуда. Когда
обеими целями стали настоящие базы, третья копия сообщений осталась без владельца:
её некому читать (читалки — Phanpy и панель диалогов) и незачем держать (долгую историю
хранят Chatwoot и GoToSocial).

Локально остаётся состояние коллектора — килобайты, не хранилище:

| Что | Зачем |
|---|---|
| курсоры | где остановились по каждому чату; без них перезапуск перечитывает всё заново |
| ключи дедупликации | цель уникальность не обеспечивает, а пересечение догона с подпиской заложено в дизайн коллектора намеренно |
| outbox | принять вебхук, ответить 200 сразу, отправить когда получится |

Heartbeat из списка выпадает: у коллектора появляется HTTP-слушатель под вебхуки, и
панель спрашивает состояние прямо у него, вместо отметок в общем файле.

Формат этого состояния — вопрос реализации, не архитектуры.

## Маршрутизация

Тип чата решает, куда уходит сообщение. Дискриминатор в коде есть, но **объявлен
неверно и требует починки до всего остального** (см. ниже).

| Тип чата | Куда |
|---|---|
| приватный диалог | Chatwoot |
| `group`, `supergroup` | Chatwoot, опционально дополнительно в GoToSocial |
| `channel` — вещание | GoToSocial |
| `gigagroup` — вещательная группа | GoToSocial |
| `monoforum` | уточнить на живых данных |

### Дискриминатор читает не то поле

`IncomingMessage.chatKind` заполняется из `message.chat.type`
([src/telegram.ts](../../../src/telegram.ts)) и объявлен как `'user' | 'chat' | 'channel'`.

В mtcute 0.28 `Message.chat` — это `Peer`, то есть `User | Chat`, а `.type` у них —
**дискриминатор объединения**, а не вид чата: у `User` это литерал `"user"`, у `Chat` —
литерал `"chat"`. Вид чата лежит в отдельном свойстве `Chat.chatType` со значениями
`'group' | 'supergroup' | 'channel' | 'gigagroup' | 'monoforum'`.

Отсюда фактическое положение дел:

| Объявлено | Приходит ли | Что на самом деле |
|---|---|---|
| `'user'` | да | приватный диалог; бот отличается через `User.isBot` |
| `'chat'` | да | **любая** группа, супергруппа, канал и гигагруппа разом |
| `'channel'` | никогда | вид чата живёт в `chatType`, а не в `type` |

Поэтому `WATCH_PRIVATE=1` в `bin/collect.mjs` работает — `'user'` настоящее значение.
А вот **новостной канал и рабочая супергруппа сегодня неразличимы**: у обоих
`type === 'chat'`. Ровно то различение, на котором держится маршрутизация.

Компилятор молчит, потому что `MessageLike` в `telegram.ts` — рукописная заглушка,
а не импорт типов mtcute. Починка: читать `chatType` при `type === 'chat'`.

Реестр отслеживаемых чатов может переопределять маршрут поштучно. Заявка может жить
в обеих проекциях одновременно — это два независимых факта, а не взаимоисключающее
состояние.

## Обратный путь: ответы

```
Chatwoot UI: человек пишет ответ
        │ вебхук message_created (outgoing)
        ▼
  слушатель в КОЛЛЕКТОРЕ ──► outbox   ← отвечает 200 сразу
                                │
                                ▼
                         MTProto send → Telegram
                                │
                                ▼
                      отметка об отправке + статус обратно в Chatwoot
```

**Приём отвязан от отправки намеренно.** Вебхуки Chatwoot имеют таймаут и ретраи: если
отправить синхронно и MTProto затормозит, Chatwoot сочтёт доставку провалившейся и
повторит запрос — в чат уйдёт дубль.

**Слушатель живёт в коллекторе, а не в харнессе**, потому что сессию MTProto держит
коллектор: он вынесен отдельным процессом из-за нативного модуля, который иначе роняет
харнесс целиком.

Три места, где наивная реализация ломается:

1. **Эхо.** Отправленное через MTProto сообщение вернётся в поток подписки, станет
   заявкой и уедет в Chatwoot дублем ответа. Гасится проверкой ключа отправленного
   при приёме. Без этого получается петля.
2. **Отправка есть только у Telegram.** MTS.Link в коде пока не читается, не то что
   пишется. В первой версии Chatwoot UI для остальных каналов работает на чтение,
   и это должно быть видно в интерфейсе, а не глотаться молча.
3. **Провал отправки обязан быть виден.** Иначе Chatwoot показывает «отправлено», а
   сообщение не ушло, и человек уверен, что ответил.

## Проверенные ограничения

Три факта проверены на живом стенде и в исходниках, а не предположены.

**Chatwoot не обеспечивает уникальность `source_id` у сообщений.** В `db/schema.rb`
индекс `index_messages_on_source_id` не уникальный — уникальность есть только у
`contact_inboxes`. Дедупликацию делегировать нельзя, она остаётся на стороне коллектора.

**GoToSocial не умеет бэкдейтить статусы.** Mastodon API не принимает `created_at` при
создании, только `scheduled_at` и только в будущее. Догон после простоя машины ляжет
в ленту временем «сейчас»; порядок сохранится, абсолютное время — нет.

**Chatwoot не поддерживает запуск под подпутём.** `RAILS_RELATIVE_URL_ROOT` не
упоминается ни в `config/`, ни в `app/`, ни в `lib/`, ни в `.env.example`. Схема
«один origin, разные пути» отпадает.

## Панель харнесса

Оболочка с двумя режимами.

**Лента** — iframe на собственный форк Phanpy. Форк self-hosted, заголовки под контролем,
`frame-ancestors` настраивается. Preact внутри iframe изолирован и правило чистоты
бандла не нарушает.

**Диалоги** — свои React-компоненты поверх REST API Chatwoot. Собственный UI выбран
не ради красоты: Chatwoot отдаёт `X-Frame-Options: SAMEORIGIN`, переопределить это в
его конфигурации нечем, а подпуть не поддерживается. Свой интерфейс снимает разом всё:
iframe не нужен, кросс-origin проблем нет, второго фреймворк-рантайма нет. CORS уже
открыт — `CW_API_ONLY_SERVER=true`.

## Нерушимые принципы после разворота

Оба принципа из [docs/PRINCIPLES.md](../../PRINCIPLES.md) остаются в силе, но меняют смысл.

**Доступ к данным только через порт** — порт теперь ведёт не к локальному хранилищу,
а к двум внешним API. Требование прежнее: панель не знает, с чем разговаривает.

**Внешние идентификаторы с самого начала** — из подготовки к переносу превратился
в несущую конструкцию. `chatId` + `msgId` становятся `source_id` в Chatwoot и
`Idempotency-Key` в GoToSocial. Без этого принципа схема без локального хранилища
не собралась бы: дедуплицировать было бы нечем.

## Лицензии

| Источник | Лицензия | Использование |
|---|---|---|
| `chatwoot/chatwoot` вне `enterprise/` | MIT | да, `app/javascript/dashboard/**` — эталон для своего UI |
| Phanpy | MIT | да, форк законен |
| `chatwoot/ui` | отсутствует | см. ниже |

У `chatwoot/ui` лицензии нет, что по умолчанию означает «все права защищены».
[docs/chatwoot-as-backend.md](../../chatwoot-as-backend.md) фиксирует это как запрет
заимствования. **2026-09-11 заказчик решил, что брать оттуда можно** — решение записано
здесь как его, вопреки собственному более раннему разбору.

Независимо от лицензии заимствовать оттуда невыгодно: репозиторий заброшен в марте
2023 и написан на Vue 2 с Foundation, тогда как актуальная версия того же интерфейса
лежит в основном репозитории под MIT и поддерживается.

## Порядок реализации

Работа не помещается в один план: это шесть самостоятельных кусков. Порядок выбран
так, чтобы каждый этап заканчивался работающей системой, а не полуфабрикатом.

| Этап | Что делаем | Почему здесь |
|---|---|---|
| 1 | Маршрутизация по `chatKind` поверх нынешнего хранилища | дешёвая правка, проверяет разметку потока до переезда |
| 2 | Проекция в Chatwoot через API-канал, дедупликация по `source_id` | основной объём потока; заодно проверяет схему без локального хранилища |
| 3 | Проекция в GoToSocial через Mastodon API с `Idempotency-Key` | вторая цель, механика та же |
| 4 | Снятие локального хранилища сообщений, состояние сжимается до курсоров и дедупа | делается последним: до этого момента есть куда откатиться |
| 5 | Обратный путь: слушатель вебхуков, outbox, отправка, подавление эха | самый рискованный кусок, начинается на устоявшейся схеме |
| 6 | Панель: два режима, iframe с Phanpy и свой React на REST | UI поверх готовых данных |

Этап 4 — точка невозврата: после него откат к прежней схеме означает потерю собранного.
Порядок 2→3→4 намеренно оставляет обе проекции обкатанными до того, как исчезнет
локальная копия.

## Границы этого дизайна

**В зоне:** маршрутизация по типу чата, проекция в две системы, обратный путь ответов
из Chatwoot в Telegram, панель-оболочка с двумя режимами, отказ от локального хранилища
сообщений.

**Вне зоны, требует отдельного дизайна:**

- **Промоушен из ленты в диалог.** Заказчик описал это как отдельный сценарий «с
  микроданными»: элемент ленты превращается в диалог Chatwoot. Там же лежит логика
  склейки диалогов, которую заказчик назвал объёмной.
- **Коллектор MTS.Link.** Сегодня его нет; сто чатов из оценки потока пока гипотетические.
- **Эксплуатация.** Автозапуск двух серверов рядом с харнессом, поведение раздела при
  их недоступности, резервные копии.
- **Ретенция состояния коллектора.** Сколько держать ключи дедупликации.
- **Объём кастомизации форка Phanpy.**

## Замеры стенда

Chatwoot поднят локально 2026-09-10 на `chatwoot/chatwoot:latest` (Rails + Postgres +
Redis + Sidekiq): около 1 ГБ памяти вхолостую, 3.3 ГБ образ. Разработчики заявляют
минимумом 4 ГБ и 2 ядра. При оценке в 5 000 сообщений в сутки это 3.5 сообщения в
минуту — величина, для которой Chatwoot спроектирован с запасом.
