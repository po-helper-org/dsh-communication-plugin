# Спайк: чем читать личный аккаунт Telegram

Проверяется единственный технически неочевидный кусок MVP — доступ к личным диалогам.
Прототип лежит в [`spike/mtproto`](../spike/mtproto).

Решающий довод за mtcute — не звёзды, а стек: раздел харнесса собирается на TypeScript,
и коллектор на нём же не тащит в контур второй рантайм и нативную сборку.

## Что прототип делает

Реестр отслеживаемых чатов, догон пропущенного с последнего обработанного сообщения,
подписка на поток, сохранение заявок в один локальный файл SQLite, разбор из командной
строки: список Inbox, карточка с тредом, пометка разобранного.

```sh
cd spike/mtproto && npm install
export TG_API_ID=... TG_API_HASH=...        # my.telegram.org
node collect.mjs                            # вход в аккаунт, догон, затем поток
node inbox.mjs                              # список Inbox
node inbox.mjs show telegram:-100500:12     # карточка с тредом
node inbox.mjs done telegram:-100500:12     # разобрано
```

Проверка логики хранилища без сети и без аккаунта:

```sh
node selftest.mjs
```

## Что закрыто

| Критерий из #2 | Статус |
|---|---|
| Заявка канало-независимой формы, состояние по умолчанию `inbox`, пустое поле класса | Закрыт, проверено selftest |
| Тред: что было до и после сообщения | Закрыт. Соседи по чату отдаются из локальной базы, второй запрос в сеть не нужен |
| Повторный проход не создаёт дублей и не сбрасывает разбор | Закрыт, проверено selftest |
| Продолжение с последнего обработанного сообщения после перезапуска | Закрыт на уровне логики: курсор на чат, догон идёт от свежих к старым до курсора |
| Пометка заявок, пришедших с задержкой | Закрыт, проверено selftest на бюджете в пять минут |
| Вложения помечаются, ссылки выделяются отдельно | Закрыт, проверено selftest |
| Хранилище локальное, без сервера СУБД | Закрыт: `node:sqlite`, один файл, ноль внешних зависимостей хранилища |
| Методы клиента, на которых держится коллектор | Закрыт: `start`, `resolvePeer`, `iterHistory`, `getHistory`, `onNewMessage` существуют в установленной версии |

## Замер задержки

Инструмент готов: `bin/measure-latency.mjs`. Два режима.

```sh
node bin/measure-latency.mjs --report --db <путь к inbox.db>   # по собранному, без Telegram
node bin/measure-latency.mjs --chat me --count 5 --db <путь>   # контрольный прогон
```

Отчёт считает по тому, что заявка и так несёт: время отправки в канале и время попадания
в базу. Отдельной телеметрии не заводится.

Контрольный прогон шлёт маркеры в «Избранное» и меряет два отрезка: отправка → событие
у клиента (транспорт) и отправка → заявка в базе (сквозная). Точка отсчёта — время сервера
Telegram, поэтому замер не зависит от расхождения локальных часов с серверными. Сквозной
отрезок считается, только если чат замера есть в реестре отслеживаемых.

Прогон требует готовой сессии и идёт от аккаунта владельца.

## Что осталось непроверенным

Требует прогона владельцем аккаунта: авторизация выполняется вводом кода из Telegram,
и делает это только владелец.

- Фактическая задержка. Инструмент замера написан и проверен в режиме отчёта на живой
  базе раздела; цифр нет, пока нет сессии. Ожидание — секунды: MTProto держит соединение
  и присылает обновления сам, опроса нет.
- Поведение на разрыве сети и после сна машины: догон написан, но на живом аккаунте не гонялся.
- Риск блокировки аккаунта. Заказчик принял его на себя; прототип читает и не пишет,
  что снижает, но не снимает риск.
- Объём базы на реальном потоке.
