# Как устроен сервис

Раздел «Управление коммуникацией» — это не один компонент, а два процесса и один файл.
Разделение не косметическое: каждая граница поставлена под конкретную беду, которая
уже случалась на живом стенде.

```
   каналы                 коллектор                 хранилище            потребитель
┌────────────┐        ┌────────────────┐        ┌──────────────┐      ┌──────────────┐
│  Telegram  │──MTProto──▶               │        │              │      │ раздел       │
│  почта     │──IMAP───▶  сбор, догон,   │──────▶ │  SQLite,     │◀─────│ харнесса     │
│  MTS.Link  │──API────▶  разметка       │        │  один файл   │      │ (только чтение)│
└────────────┘        └────────────────┘        └──────────────┘      └──────────────┘
                              │                          ▲
                              └── отметки о себе ────────┘
```

## Почему коллектор — отдельный процесс

Клиент Telegram тянет нативный модуль (`better-sqlite3` для хранилища сессии). Когда он
жил внутри харнесса, несовместимый бинарь уронил **весь харнесс целиком**, а не свой
раздел: `dsh: fatal load failure`, порт перестал слушаться, launchd крутил рестарт по кругу.

Поэтому раздел не импортирует клиента даже транзитивно: `src/telegram.ts` намеренно
не реэкспортируется из `src/index.ts`. Раздел читает базу через встроенный `node:sqlite` —
ноль нативных модулей, ронять нечем.

Побочная выгода: коллектор переживает перезапуск харнесса, а харнесс — падение коллектора.
О состоянии сбора раздел узнаёт по отметкам в базе (`collector.seenAt` не старше двух
минут), и если сбор не идёт, панель говорит об этом прямо, а не показывает пустой Inbox
как норму.

## Порядок запуска коллектора

1. **Вход по сохранённой сессии.** Код подтверждения приходит в приложение Telegram, и
   спросить его некому — харнесс поднимает раздел без терминала. Сессия заводится один раз
   командой `bin/login.mjs`.
2. **Запуск потока обновлений.** `connect()` его не поднимает: без явного
   `startUpdatesLoop()` подписка молча не срабатывает, и коллектор собирает историю
   и больше ничего. Проверено замером: пять маркеров подряд без единого события.
3. **Подписка — раньше чтения.** Между концом догона и началом подписки есть окно, и
   сообщение, пришедшее в него, не попало бы никуда.
4. **Догон непрочитанного** по каждому чату, изолированно: отказ по одному не отменяет
   остальные.
5. **Отметка о себе** раз в полминуты, пока процесс жив.

## Правила сбора

**Порог догона** берётся от последнего прочитанного человеком, а не от нашего курсора:
сообщение могло быть собрано прошлым запуском, но человеком не прочитано. Порог снимается
один раз до чтения — пересчёт по ходу обрывал бы догон на первом же сообщении, потому что
параллельная подписка двигает курсор вперёд.

**Дубли** отсекает ключ заявки `{канал}:{чат}:{сообщение}`, а не порог. Поэтому пороги
можно ставить с запасом, а повторный проход безопасен: он не создаёт копий и не сбрасывает
уже проставленное состояние разбора.

**Границы** задаются папками Telegram: их состав человек ведёт в клиенте, и он меняется
вместе с папкой. Отдельные чаты добавляются к папкам. `WATCH_PRIVATE=1` принимает любые
личные сообщения, включая диалоги, которых ещё нет — сообщение с незнакомого аккаунта
заводит новый чат, и никакой реестр его заранее не содержит.

**Задержка.** Заявка, собранная позже бюджета (по умолчанию 5 минут) с момента отправки,
помечается признаком задержки. Догонять простой машины раздел не обязан, скрывать его —
обязан не. Замер на живом аккаунте: медиана 0.63 с, максимум 1.07 с.

**Ничего не помечается прочитанным** в самом канале: чтение через MTProto не отправляет
отметок, и собеседник не видит, что вы «прочитали».

## Формат заявки

Канало-независимый по построению: канал — поле, а не структура. Почта и MTS.Link
добавляются коллекторами, а не переделкой модели.

```json
{
  "key": "telegram:-1001234567890:8421",
  "channel": "telegram",
  "chatId": "-1001234567890",
  "chatTitle": "Платформа / релизы",
  "msgId": 8421,
  "threadKey": "telegram:-1001234567890",
  "author": "Дмитрий Карпов",
  "authorId": "77712345",
  "sentAt": 1757447880000,
  "receivedAt": 1757447883100,
  "delayed": false,
  "text": "@Алексей нужен твой ответ по флагу витрины",
  "hasMedia": false,
  "links": ["https://tracker.example.ru/browse/GDSLV-1834"],
  "state": "inbox",
  "class": null,
  "labels": ["sprint", "answer"]
}
```

Два поля существуют ради будущего и заполняются уже сейчас:

- **`authorId`** — автор в терминах канала. Отображаемое имя меняется, идентификатор нет,
  поэтому сопоставление с внешней системой держится на нём.
- **`labels`** — идентификаторы из справочника раздела. Подпись и цвет живут в справочнике,
  поэтому переименование лейбла не трогает ни одной заявки.

## Состояния и разметка

Состояний два: `inbox` и `разобрано`. Значение по умолчанию — `inbox`, **других путей
появления заявки нет**: ничто не отсеивается молча, ничто не попадает в бэклог само.
Третьим значением сюда встанет `to-review`, когда появится разметчик.

Лейблы — основа разметки, независимая от состояния. Сейчас их ставит человек, дальше
будет ставить модель; кто поставил, видно по начертанию чипа, потому что доверие
к разметке зависит от её происхождения.

## Что раздел не делает

Не пишет в бэклог. Не отправляет ничего в канал: отправку наружу всегда подтверждает
человек. Не заводит второго хранилища одних и тех же сущностей. Не ходит в базу из панели —
только подкомандами канала, иначе смена хранилища потребует переписать интерфейс
(см. [PRINCIPLES.md](PRINCIPLES.md)).

## Проверки

```sh
npm test                             # 23 теста, без сети и без аккаунта
RUN_LIVE_TESTS=1 npm run test:live   # 6 тестов на живом аккаунте, только чтение
```

Обычный круг работает подделкой порта канала: клиент приходит параметром, поэтому логика
сбора проверяется без Telegram. Живой круг проверяет то, что подделка проверить не может —
что система действительно читает данные.
