# Нерушимые принципы раздела

Два правила, которые не обсуждаются при доработках и не отменяются ради удобства
отдельной задачи. Их смысл — сохранить возможность сменить хранилище (сегодня SQLite,
завтра Chatwoot или что-то ещё) без переписывания раздела.

Нарушение любого из них — повод вернуть изменение, а не обсуждать компромисс.

## 1. Доступ к данным только через порт

Хранилище скрыто за портом. Сегодня это `InboxStore` поверх SQLite; завтра рядом встаёт
реализация поверх внешнего API, и ни канал `/communication`, ни панель не меняются вовсе.

Что это запрещает:

- панель ходит в базу напрямую — запрещено. Панель знает только подкоманды канала;
- панель знает форму строки таблицы, имена столбцов, диалект SQL — запрещено;
- канал возвращает наружу сырые строки хранилища вместо модели — запрещено;
- бизнес-логика живёт в SQL — запрещено: она уезжает вместе со сменой хранилища;
- новый источник данных подключается мимо порта — запрещено.

Проверка при ревью: если удалить `store.ts` и написать другую реализацию того же
интерфейса, должны ли поменяться `channel.ts` и `src/client`? Ответ обязан быть «нет».

## 2. Внешние идентификаторы хранятся с самого начала

Заявка несёт идентификаторы канала: чат, сообщение, автор — в терминах самого канала,
а не в отображаемом виде. Тогда сопоставление с внешней системой делается переносом
того, что уже собрано, а не повторным сбором истории из канала.

Что это запрещает:

- хранить только отображаемое имя автора: имя меняется, идентификатор — нет;
- собирать чат по названию: название меняется, а перенос по нему разъедется;
- считать ключ заявки достаточным: он наш, внешняя система его не знает.

Проверка при ревью: можно ли по сохранённой заявке найти тот же диалог во внешней
системе, не обращаясь к каналу? Ответ обязан быть «да».

Схема догоняется миграцией по столбцам (`InboxStore.migrate`): база владельца
не пересоздаётся и собранные заявки не теряются.

## Состояние на сегодня

Оба условия выполнены. Панель ходит только в канал, канал отдаёт модель, а не строки
хранилища; заявка несёт `chatId`, `msgId` и `authorId` в терминах канала.

Идентификатор автора добавлен позже остальных — при первой же сверке кода с принципом
оказалось, что хранилось только отображаемое имя. Столбец добавлен миграцией.
