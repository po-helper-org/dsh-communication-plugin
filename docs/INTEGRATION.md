# Независимость и совместимость

Два требования, которые легко перепутать, но они про разное.

**Независимость.** Коллектор обязан работать сам по себе: подключить ящики, собрать поток,
отдать наружу. Ни харнесс, ни Chatwoot, ни какой угодно другой бэкенд не должны быть
условием его работы.

**Совместимость.** Когда поток понадобится отдавать в Chatwoot, это должно стоить одну
реализацию доставки, а не переписывание сбора.

Оба требования выполняются одним решением: **у коллектора есть выход, и выход — порт**.

## Слои и их зависимости

```
bin/collect.mjs           процесс: читает .env, поднимает клиент, гоняет цикл
   │
   ├── src/telegram.ts    единственное место, знающее про Telegram (и про нативный модуль)
   ├── src/collector.ts   правила сбора. Клиент приходит портом ChannelPort
   └── приёмник           куда складывать заявки
          │
          ├── InboxStore (сейчас)      SQLite, один файл, без сервера
          ├── Chatwoot (следующий)     API-канал: контакт, диалог, сообщения
          └── любой другой             вебхук, очередь, файл JSONL
```

Ни один слой не знает про соседей больше, чем через свой порт. `collector.ts` не
импортирует ни `telegram.ts`, ни драйвер базы: он получает клиента параметром и пишет
через интерфейс хранилища. Поэтому вся логика сбора проверяется без сети и без аккаунта.

## Контракт приёмника

Приёмник заявок — четыре метода, которыми пользуется коллектор. Больше ему ничего не нужно:

| Метод | Зачем |
|---|---|
| `save(item): boolean` | Положить заявку. `false` — такая уже есть, дубля не создаём |
| `cursor(chatId): number` | Последнее обработанное сообщение чата |
| `advanceCursor(chatId, msgId)` | Сдвинуть курсор после успешной записи |
| `setMeta(key, value)` | Отметки о самом коллекторе: жив, что смотрит, последняя ошибка |

`InboxStore` — реализация поверх SQLite. Реализация поверх Chatwoot API кладёт заявку
как сообщение в диалоге, курсор держит у себя или в `custom_attributes`, а отметки шлёт
как атрибуты ящика. Коллектор об этой разнице не узнает.

Курсор и дедупликация обязаны жить рядом с приёмником, а не в коллекторе: иначе при смене
приёмника сбор начнёт заново читать историю и создаст дубли в новом хранилище.

## Соответствие модели Chatwoot

Наша заявка ложится на объекты Chatwoot почти дословно — это и делает переход дешёвым.

| Заявка | Chatwoot | Замечание |
|---|---|---|
| `channel` | Inbox типа **API** | Один ящик на канал. Нативный Telegram-канал Chatwoot не годится: он на Bot API и личных диалогов не отдаёт |
| `chatId`, `chatTitle` | Conversation | Диалог заводится на первый входящий, дальше ищется по `source_id` |
| `threadKey` | Conversation | У нас тред равен чату; в Chatwoot это то же самое |
| `msgId` | Message `source_id` | Ключ идемпотентности: повторная отправка не создаёт копию |
| `author`, `authorId` | Contact `name`, `identifier` | Именно поэтому `authorId` хранится с самого начала |
| `sentAt` | `created_at` сообщения | Chatwoot принимает своё время; исходное едет в `content_attributes` |
| `receivedAt`, `delayed` | `content_attributes` | Своего поля у них нет, а терять признак задержки нельзя |
| `text` | `content` | |
| `hasMedia`, вложения | attachments | Файлы у нас пока не скачиваются (issue #8) |
| `links` | `content_attributes` | |
| `labels` | Conversation labels | Совпадает по смыслу: и там и там метка на диалоге, справочник общий |
| `state` `inbox` / `разобрано` | `open` / `resolved` | Прямое соответствие |
| `class` | — | Поле под будущую модель, у них аналога нет |

Что не ложится и не должно: обоснование разметки («почему модель так решила»). У Chatwoot
метки ставит человек, объяснять их некому. Это поле остаётся нашим и живёт рядом с заявкой.

## Работа без харнесса

Коллектор — обычный процесс Node без единой зависимости от харнесса:

```sh
node bin/login.mjs        # один раз: вход в аккаунт
node bin/collect.mjs      # сбор: папки и чаты из .env
node bin/dialogs.mjs --folders   # что вообще есть в аккаунте
node bin/measure-latency.mjs --report   # задержка по собранному
```

Результат — файл SQLite, который читает кто угодно: раздел харнесса, скрипт, другой сервис.
Схема из семи колонок описана в [ARCHITECTURE.md](ARCHITECTURE.md), догоняется миграцией
по столбцам и не пересоздаёт базу владельца.

Обратное тоже верно: раздел харнесса не требует коллектора, чтобы подняться. Нет сбора —
панель открывается и говорит, чего не хватает.

## Порядок работ

1. **Сейчас.** Приёмник один — SQLite. Контракт соблюдён по факту: коллектор пишет через
   интерфейс, а не через драйвер.
2. **Следующий шаг, когда понадобится.** Вынести контракт приёмника в явный тип и завести
   вторую реализацию — доставку по HTTP (вебхук или Chatwoot API). Коллектор не меняется.
3. **Переход на Chatwoot как бэкенд** — отдельное решение с ценой в 4 ГБ памяти и четыре
   процесса, см. [chatwoot-as-backend.md](chatwoot-as-backend.md). Совместимость модели,
   описанная выше, нужна независимо от того, состоится переход или нет: она же описывает,
   как отдавать поток в любой другой сервис.
